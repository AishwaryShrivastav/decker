# Decker v0.1.4 design

## Decision

Decker v0.1.4 will support two direct, bring-your-own-key paths: OpenAI and
Gemini. Claude is outside the release. A user chooses one provider, Decker
validates the key before saving it, and that provider handles transcription,
topic work, research, and artifact generation without a Decker server.

The extension will record any eligible active browser tab, including
browser-based meeting tools. A muted tab or a tab with no recent audio produces
a warning; the captured track and signal checks determine whether recording can
continue. Native meeting apps are unsupported because a browser extension
cannot capture their audio.

## Product flow

The popup has three jobs:

1. **Setup:** choose OpenAI or Gemini, enter a key, and save only after a live
   provider check succeeds.
2. **Readiness:** show whether the active tab can be captured and whether the
   microphone is available, with clear help for muted or unsupported tabs.
3. **Recording:** start, stop, and show capture or transcription progress.

Transcript review, topic selection, instructions, format choice, generation,
and download move to a dedicated extension page. Stopping a recording opens
that page. Recovery continues to use the existing local session record.

## Provider architecture

A typed provider adapter owns key validation, audio transcription, ordinary
text generation, and streamed text generation. A registry resolves `openai` or
`gemini`; shared capture and generation code never branches on provider names.

Provider settings are stored locally as a versioned active-provider record.
On first load, an existing `openaiKey` becomes an OpenAI provider setting so
v0.1.3 users keep working without re-entering their key. The current popup's
OpenAI-shaped message contract remains compatible during the foundation pass.

OpenAI keeps the current Whisper and GPT behavior. Gemini uses its Models API
for validation, Files and Interactions APIs for transcription, and
GenerateContent endpoints for text. Requests go directly from the extension to
the selected provider. The manifest grants access only to the OpenAI and Gemini
API origins.

## Public claims

Website, privacy, and store copy will use the style rules in
`/Users/aishwary/Downloads/AISlopRemoverAUg'26Version.md`: direct sentences,
specific claims, varied rhythm, and little formatting. Public copy will state:

- OpenAI or Gemini key required; provider charges may apply;
- keys and recovery data stay in local extension storage;
- meeting content goes directly to the selected provider;
- eligible browser meeting tabs can be captured, with silence and mute warnings;
- native meeting apps are unsupported;
- Decker has no meeting bot and receives no automatic meeting-content telemetry.

No copy will imply support for Claude, native-app audio, every website, or
capture blocked by browser or organization policy.

## Release boundaries

The first implementation commit covers only the provider foundation: adapter,
registry, provider calls, settings migration, background wiring, permissions,
and tests. It does not change the popup layout, add the review page, rewrite the
site, update store copy or ZIPs, bump the version, publish, or push.

The complete v0.1.4 release requires extension tests, typecheck, Chrome build,
website build, manual OpenAI and Gemini checks, capture checks on more than one
browser meeting site, privacy and store review, and ZIP verification.

Decker v0.1.4 is Chrome-only. Firefox packaging is disabled until Firefox has a
working capture and recorder path.

## Alternatives considered

- Extending the current worker with provider conditionals would be quick, but
  provider behavior would leak through capture and generation code.
- Adopting provider SDKs would reduce some HTTP code, but increase bundle size
  and permissions for a two-provider browser extension.
- The selected adapter and registry keep the shared pipeline small, preserve the
  current OpenAI flow, and leave room for provider-specific HTTP details.
